# Additive history schema v2

The file remains `history.v1.db`; the name is stable while `PRAGMA user_version` becomes 2. The production owner remains SqliteHistoryStore with its exclusive file lease, serialized off-thread worker, two-second busy timeout, DELETE journal, FULL synchronous commits, existing capacity policy and backups. No second SQLite connection is introduced for diagnostic production writes. Foreign keys are enabled for new entities.

Before modifying a genuine version-1 database, the owner performs SQLite BackupDatabase into a unique closed `history-before-diagnostics-v2-*.db`, runs quick_check, then renames the verified snapshot. Failure leaves the schema unchanged. Keep this original-schema backup. v0.1.1 cannot read schema v2; rollback means restore a COPY of the backup into an isolated v0.1.1 workspace together with the original configuration/preferences. Never replace the only live archive or overwrite release archives. Backups contain sensitive unredacted local evidence.

One transaction creates diagnostic_sessions, diagnostic_results, diagnostic_observations, diagnostic_baselines and diagnostic_comparisons plus indexes, and changes user_version. Existing outages, events, sessions, metadata and storage_policy records are preserved. A failed migration rolls back all new tables and schema version. Already-oversized files receive bounded migration page headroom before the existing capacity limit is reapplied. A database too full to accommodate schema growth fails safely instead of deleting incidents.

Diagnostic incident references are real foreign keys to outages; nonexistent incidents are rejected. Child IDs cannot move across sessions. Saved request identity and all checkpointed results are append-only. Terminal sessions are immutable. Baselines require all requested tests to have successful complete evidence. Each network call runs outside transactions; completed child tests checkpoint independently. A crash during a test can lose its not-yet-saved samples, but retained prior tests survive. Startup marks pending/running checkpoints Interrupted without assigning a fabricated completion timestamp or incident recovery.

Queries return at most 100 summaries, 50 per UI page using a timestamp-plus-ID cursor. A single session is limited to seven tests and a 2 MB serialized payload; observations and probe counts are bounded. Existing opt-in monitoring retention preserves an entire monitoring session if its incidents have linked diagnostic evidence. Baselines/comparisons pin their source records. Confirmed session deletion rejects active or referenced sessions and cascades normalized children. Confirmed baseline deletion atomically removes its comparisons and preserves source sessions. Existing opt-in retention removes old terminal standalone diagnostics with known completion times and no references; unfinished checkpoints and incident links are preserved. No new schema version is needed. A full shared store fails visibly and preserves history. Backup/capacity management remains available through Preferences.

Automated migration fixtures exercise v1 schema and policy preservation. Genuine v0.1.1 copied-data upgrade evidence, source hashes and restart outcomes are recorded separately in TEST_REPORT.md; a constructed fixture alone is not claimed as genuine user-data certification.
